2. A2A 进程内调度器 评分 A

2.1 A2A_AGENTS 注册表 — 为什么需要它?

a2a_dispatcher.py:19-36 定义了一个硬编码的静态路由表。它与 registry.py 的自动发现不同——A2A 层面临三个 registry.py 无法解决的问题：

问题 1: registry.py 只注册元信息，不包含模块路径
  DomainPlugin 有 name/port/capabilities，但没有"这个 Agent 的 root.py 在哪个文件"
  → A2A_AGENTS 补充: "pharmacy" → "agents.domains.haip.pharmacy.root"

问题 2: 不是所有 Agent 都可以 A2A 调用
  CLI-only 的 Agent (togaf/nx/haip portal) 没有实现 dispatch_entry()
  → A2A_AGENTS 通过"白名单"机制排除不可调用的 Agent

问题 3: 调用方不需要 import 整个 Agent 包
  Agent 的 __init__.py 可能触发副作用 (数据库连接/模型加载)
  → A2A_AGENTS 指定只 import root 模块, 绕过 __init__.py 的副作用

本质上 A2A_AGENTS 是 Agent 的 DNS 解析表——将 "agent 名字" 翻译为 "模块路径"，用最小的 import 开销获得可执行入口。

2.3 Agent 端契约: dispatch_entry() — 统一入口函数

每个 Agent 的 root.py 必须导出 dispatch_entry(tool, params) -> dict。它的作用是将 Agent 内部的功能函数暴露为 A2A 可调用的标准化接口——调用方不需要知道 Agent 内部有哪些模块、哪些函数，只需知道 tool 名称即可。

以药剂科为例 (root.py:523-566)：

def dispatch_entry(tool, params):
  # 内部路由表 — 将外部 tool 名映射到内部函数
  tools = {
    "assess_nutrition": assess_nutrition_risk,
    "calculate_tpn": calculate_tpn,
    "review_prescription": review_prescription,
    "list_rules": list_rules,
    "list_medications": list_medications,
    "recommend_route": recommend_nutrition_route,
  }
  if tool in tools: return tools[tool](**params)
  return {"status": "error", "error": f"Unknown tool: {tool}"}

dispatch_entry 的三个核心职责：

职责说明示例
1. 能力暴露将 Agent 内部分散的功能函数 (可能在 core/ 下的不同模块) 集中注册为一个统一菜单药剂科 6 个 tool 对应 6 个独立的 core/ 模块
2. 输入校验检查 tool 名称是否在支持列表中, 对未知 tool 返回标准化 error{"status": "error", "error": "Unknown tool: xxx"}
3. 输出标准化确保返回 {"status": "ok"/"error", ...} 格式, 让 A2ADispatcher 和 Orchestrator 无需适配A2ADispatcher 只检查 result["status"] 是否为 "ok"

dispatch_entry 是契约式接口: 只要 Agent 实现了这个函数签名并返回均一化 dict, A2ADispatcher 就能透明地调用它。这也是为什么 A2A_AGENTS 只用模块路径而无需知道内部结构——dispatch_entry 本身承担了"能力发现"的职责。

  → 仅当纠正结果与原输出不同且 >20 字符时才替换

Layer 4 — 跨 Agent 交叉验证 (Cross-Validation)
  纯关键词比对 — 7 对相反术语:
    高风险/低风险, 高危/安全, 延迟/进行, 手术/保守,
    禁忌/适用, 不推荐/推荐, 停用/继续
  → 检测到分歧 → cross_validation_conflict = True

输出: GuardResult { passed, flags, citations, confidence, corrected_output, requires_human_review }

6. 引擎层工作原理

引擎层 (src/agents/harness/, 38 个文件) 是平台的运行时核心，提供 Agent Loop、工具系统、LLM 调用三大能力。

6.1 Agent Loop (ReAct 模式) — agent_loop.py 254 行

针对 Web 集成场景设计的 ReAct 执行循环。使用 OpenAI function calling API (非 smolagents Python 沙箱)，因为 "Nexent CodeAgent 沙箱不会将 MCP 工具注入为可调用的 Python 函数"。

关键参数: max_steps=5, temperature=0.3, max_tokens=4096, LLM 超时=120s

AgentLoop.run(query):
  for step in 1..max_steps:
    1. _call_llm(messages, allow_tools=True)
       → 构建 OpenAI function calling 请求
       → 所有已注册 BaseTool → OpenAI tool schema
    2. 响应无 tool_calls → LLM 返回最终回答 → LoopResult
    3. 有 tool_calls → 逐个执行:
       execute_tool(name, **args) → ToolResult
       assistant message + tool message 追加到对话
    4. 回到步骤 1 继续
  → 达到 max_steps: "已达到最大推理步数"

6.2 工具系统 — BaseTool + Tool Registry

base_tool.py (27 行) 定义了统一的工具接口。每个工具继承 BaseTool(ABC)，必须实现 execute(**kwargs) -> ToolResult。

组件说明
ToolResult (Pydantic)success, output, error, data, citations, confidence — 均一化工具返回值
BaseTool (ABC)name, description, parameters(), execute() — Agent Loop 将其转为 OpenAI function schema
register_tool(tool)将 Tool 实例注册到全局 _tools: dict，以 tool.name 为键
discover_tools()使用 pkgutil 扫描 agents.harness + agents.rules.mcp_tools 的 register_tools()
execute_tool(name, **kwargs)从注册表查找 → 调用 execute() → 返回 ToolResult

6.3 LLM 客户端 — llm.py 268 行

三合一 LLM 接口：标准调用 + 结构化输出 + 流式输出。API Key 优先级: DEEPSEEK_API_KEY > OPENAI_API_KEY > opencode.json 配置文件。

函数用途关键参数
call_llm()标准文本/工具调用对话temperature=0.3, max_tokens=4096, model="deepseek-chat"
call_llm_structured()强制 JSON 结构化输出temperature=0.1, output_schema 注入 system prompt
call_llm_stream()SSE 流式输出 (生成器)逐行解析 SSE data 块，yield content chunk

所有调用使用 urllib.request (Python 标准库)，无 requests/httpx/openai SDK 依赖。Bearer 认证，120s 超时。无重试逻辑。Token 追踪通过可选的 agents.domains.token.core.tracker 模块记录。

当前流程依赖开发人员遵循 haip-asset-guide.md 的手工规范。理想状态下应在 CI 中增加元模型校验: 扫描所有 YAML 的 type 字段, 与 ENTITY_TYPES 注册表比对, 发现未知类型即告警。这将把"手工规范"升级为"自动化门禁"。

置信度计算 — 从引用到决策的完整链路

加权公式: 来源质量(0.35) + 工具可靠性(0.25) + LLM 确定性(0.25) + 交叉验证(0.15)

来源质量子评分:
  无引用 → 0.3  |  ≥50% T1 → 1.0  |  ≥50% 已验证 → 0.8  |  其他 → 0.6

决策阈值:
  ≥ 0.8 → 通过  |  0.6-0.8 → 标注  |  0.3-0.6 → 审查  |  < 0.3 → 阻止
设计意图: 来源质量占比最高 (35%)，体现"知识可信度是 AI 输出可信度的基础"这一设计理念。T1 来源密度直接决定置信度能否 ≥0.8 通过阈值 — 如果全部引用来自 T2 来源，仅来源质量一项就会被限制在 0.6，加上 LLM 不确定性和工具波动，很难达到 0.8 的直接通过线。

规则引擎架构剖析

规则资产中心是平台中唯一被标记为 rules 类型的 Agent，含 11 个 Python 文件，实现从规则 YAML 加载、表达式求值、冲突仲裁到变更治理的完整闭环。

GuidelineSource (指南来源)

仲裁引擎: 四阶段冲突解决

evaluate_rules(rules, context):
  0 条匹配 → "无法判定" (WEAK)
  1 条匹配 → 直接返回 winner (single_match)
  多条匹配:
    1. 检测冲突: 同一 decision_point 下结论不同 → 进入仲裁
    2. 管理优先: 检查 conflict_policy.yaml 的 override_rules
       (管理员可指定某规则无条件胜出)
    3. 策略排序: 按 (source.admin_priority, certainty, rule.priority) 升序
       默认策略: "conservative" (保守 — 选最安全结论)
    4. 构建仲裁链: 输出带引文的推理过程
